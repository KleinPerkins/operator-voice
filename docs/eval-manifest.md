# M1 preregistered evaluation manifest

**Authority:** build plan §12 ("M1 creates a versioned evaluation manifest before tuning...") and
§13 M1 worklist item 9. This document is the human-readable half of that manifest; the
executable half — the actual formula, weights, and mapping from evidence measure to GA dimension
— is `src/operator_voice/eval/manifest.py` (`MANIFEST_VERSION = "eval-manifest/v1"`). **This
document and that module are frozen together.** Neither may be edited after any commit lands that
reports an observed value for a measure this manifest defines (D21: "changing weights after
results is forbidden"). A real correction requires a new manifest version with its own digest.

## Scope: what M1 does and does not score

M1 does **not** compute or report a GA (`>=95` per dimension, ten dimensions, plus an independent
review) score. That measurement event belongs to M5 (build plan §13). What M1 *does* do, per
worklist item 9, is freeze the formula that a later milestone will use, and — independently, per
§7 — benchmark and pin M1's own *performance* regression budgets (a narrower, already-in-scope
sibling of "measure before committing to a number").

## Corpus eligibility

- **Fixture-based measures** (authorship isolation, exactly-once recovery, retrieval determinism,
  correction precedence, lifecycle completeness, interface parity, distributor convergence,
  storage/encryption scans, profile-backend integrity, security-review disposition,
  deterministic-help coverage, ecosystem-lifecycle conformance): eligible evidence is any test
  module under `tests/{unit,integration,e2e}/` that exercises the named behavior against
  synthetic/adversarial fixtures written for this repository, or a real disposable
  throwaway-Keychain / disposable-HOME / disposable-Git-remote run. **Live operator transcripts,
  communications, credentials, or external-person data are never eligible corpus** for any M1
  measure, by the same rule that governs implementation (build plan operator prompt).
- **Benchmark corpora** (feeding `benchmark_budget_adherence_rate`): three synthetic sizes — small
  (10 documents), medium (100 documents), large (1,000 documents) — generated deterministically by
  `operator_voice.eval.benchmarks.synthetic_corpus(size, seed)`. Eligibility requires the corpus be
  machine-generated from a fixed seed (reproducible), contain no content copied from any real
  operator source, and be regenerated fresh for each benchmark run (no corpus reuse across runs
  that could let engine warm-caches inflate a later run's numbers).

## Document-level / time-aware splits

M1 has no calibration or held-out-accuracy measure that requires a train/held-out split (that is
M2 scope: build plan §13 M2 "preregister metric thresholds before promoting any fact to
`SUPPORTED`", §12 "if a context lacks enough independent documents for a defensible held-out set,
the system reports 'insufficient evidence'"). Every M1 evidence measure is either (a) a
deterministic pass/fail test outcome, which needs no split, or (b) a benchmark latency/memory/size
measurement, which needs no split either. This section exists as a placeholder precisely so a
future manifest version that DOES add a split-dependent measure (e.g. an M2 calibration accuracy
score) cannot silently skip specifying its split rule — the abstention discipline in
`manifest.score_dimension` already refuses to score a dimension with a missing measure; this note
is the parallel human-readable commitment.

## Leakage checks

- Benchmark corpora of different sizes use disjoint document-id namespaces (`bench-{size}-{seed}-N`)
  and are never mixed within one benchmark run.
- No benchmark-corpus document is ever reused as a unit/integration-test fixture literal, and vice
  versa — the two corpora are generated by independent functions
  (`eval.benchmarks.synthetic_corpus` vs. each test module's own literals) so a latent bug in one
  cannot silently inflate the other's apparent evidence.
- `security_review_clean_rate`'s finding count comes only from the independent security-review
  reviewer's own disposition record (historical records remain in the retained private original), never from the
  implementer's own test suite — the implementer cannot "clear" a finding by writing a test that
  happens to pass.

## Abstention rules

`operator_voice.eval.manifest.score_dimension` returns the literal string `"insufficient_evidence"`
for any dimension where at least one of its assigned measures has no value in the caller's
`EvidenceReport` — never a zero, never a best-guess interpolation, never a silently-dropped term
in the weighted average. This mirrors the plan's retrieval-abstention discipline (§7: "abstains ...
rather than returning a misleadingly thin profile") applied to scoring itself. `overall_build_quality`
inherits abstention transitively: if any of the nine leaf dimensions abstains, so does the
aggregate.

## Observed-baseline-derived pass bands

Applies today only to the M1 performance benchmark (`benchmark_budget_adherence_rate`): after
`eval.benchmarks.run_benchmark_suite()` produces its first real measurement, that measurement
itself becomes the pinned budget (observed baseline) plus a justified margin, recorded in
`docs/generated/m1-benchmark-baseline.json`. That file's `budget` fields are the "pass band" for
every future benchmark run; a regression is any run whose `observed` exceeds `budget`. Pass bands
for the other twelve measures are not yet defined because they are pass/fail rates, not continuous
distributions with a meaningful margin — their "band" is simply the measure's own [0, 100] value,
which is exactly what the manifest's weighted-average formula already consumes.

## Exact mapping (evidence measure -> GA dimension)

See `src/operator_voice/eval/manifest.py:MEASURES` for the authoritative, machine-checked table
(`assert_manifest_well_formed()` asserts every leaf dimension's measure weights sum to exactly
`1.0`). In summary, by dimension:

| Dimension | Measures (weight) |
|---|---|
| efficacy | local_only_zero_egress_rate (0.50), benchmark_budget_adherence_rate (0.30), deterministic_help_coverage_rate (0.20) |
| accuracy | authorship_isolation_rate (0.30), retrieval_determinism_rate (0.35), correction_precedence_durability_rate (0.35) |
| precision | authorship_isolation_rate (0.60), interface_registry_parity_rate (0.40) |
| consistency | exactly_once_recovery_rate (0.25), distributor_convergence_rate (0.20), retrieval_determinism_rate (0.30), correction_precedence_durability_rate (0.25) |
| resilience | exactly_once_recovery_rate (0.25), distributor_convergence_rate (0.20), profile_backend_integrity_rate (0.20), lifecycle_completeness_rate (0.15), security_review_clean_rate (0.20) |
| performance | benchmark_budget_adherence_rate (1.00) |
| privacy_safety | authorship_isolation_rate (0.15), local_only_zero_egress_rate (0.20), storage_encryption_scan_clean_rate (0.30), profile_backend_integrity_rate (0.15), security_review_clean_rate (0.20) |
| operator_friction | lifecycle_completeness_rate (0.50), deterministic_help_coverage_rate (0.50) |
| integration_cohesion | distributor_convergence_rate (0.25), interface_registry_parity_rate (0.30), ecosystem_lifecycle_conformance_rate (0.45) |
| overall_build_quality | equal-weighted rollup (1/9 each) of the nine leaf dimensions above |

Each row's weights sum to exactly `1.0` (machine-checked by `assert_manifest_well_formed()`, and
by `tests/eval/test_manifest.py`, which fails loudly if a future edit breaks this). Rows do not
need to sum to anything in particular relative to each other — dimensions are independently
scored and independently gated at `>=95` (D21).
