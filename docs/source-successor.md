# Source successor boundary

This source-only successor starts without the original repository's Git history. The original repository, tags, historical implementation evidence and private operational/discovery records remain private and preserved. They are not inherited release evidence.

Runtime source, synthetic tests, product/reference documentation and reviewed delivery preparation are retained. This preparation does not alter installed runtimes, operator profiles, credentials, host jobs, consumer pins or original repositories. Existing old commits/tags continue to belong to the retained original; do not recreate them by importing history.

Repository identity is new. The exact clean source was admitted under the owner release. WORK source enrollment is enabled after fresh successor review, current-main CI, read-only App qualification, owner-visible controls and owner initial enrollment admission; PERSONAL remains disabled pending separate qualification. Account-bound ordinary PR creation, current review/CI/control admission, App activation and an actual App-owned native squash still require their own evidence.

Retained frozen product plans and ADRs keep their exact original bytes and repository references as accepted design provenance. Their presence does not transfer historical delivery or governance acceptance to the successor. No profile repository name, remote or fixture was retargeted by the CI identity change.

## Prepared App delivery controls

The successor enrollment retains repository-specific CI jobs, shard/skip rules and aggregate receipts. App qualification uses current controls only; retired controller blockers and bootstrap qualification are rejected. Before qualification and each App write, the actual scoped App credential must observe every contributing effective ruleset as active with `current_user_can_bypass: never`. A redacted bypass actor list does not prove this status.

Ordinary delivery rechecks the current review, CI run, source head, base and trusted policy. Existing or unknown native auto-merge requests stop admission for read-only reconciliation. A single existing App approval for the exact head may be reused; both reused and newly submitted approvals are reread before native delivery. App-only native squash or arming requires actor and state readback; ambiguous responses never trigger a blind retry. Native strict checks arbitrate later head/base races. The owner accepted the unavoidable race in which a concurrent foreign actor arms auto-merge after the last read; these checks do not claim atomic exclusion of that actor.

Q16 receipts are operational local trust, not cryptographic anti-forgery evidence. Initial source preparation did not itself qualify hosted CI, App installation/enrollment, source publication, successor name cutover or production runtime. The activation record supplies the fresh source and enrollment evidence; production runtime remains outside this source delivery.
